# Format-additions study: write-up for the reviewers

Record tags used throughout:
- **R*n*** is line *n* of `records.jsonl` (34 lines, all re-read; R2–R18 and R28, R30 re-derived from the tables on disk).
- **T*n*** is tool call *n* in `agent-tool-calls.txt`; its result exists only in the transcript.
- **L*n*** is an id in `layout-records.jsonl`, the layout run I finished on ada after the coordinator lifted the no-ssh rule for that one experiment.
- Numbers are **measured** unless marked **bound**. "Computed" means measured from the unit tables over 300 windows per size (`analyse.py`), not by a reader run; triples are median / p90 / max.

## Method and evidence standard (preregistered, verbatim, not loosened)

```
Evidence standard for a "need"
- A need is DEMONSTRATED only if all four hold:
  a. a named view or number a user would ask for, on a named hosted file, at named coordinates;
  b. today's reader output for it, obtained by running the reader (or reading its code with file:line when a run is impossible);
  c. the missing fact shown from the source graph (GFA) for that same window: a link, count, bubble or coordinate that
     exists in the input and is not derivable from any set of rows of the walk file (not just the rows one cut fetches);
     "not derivable from what a cut fetches but derivable from more fetches" is a READER COST finding, not a format gap,
     and is reported as such with its measured cost;
  d. if an approximation exists, its error measured against the truth from the GFA, with where it is wrong.
- A need supported only by an argument, a different tool's feature list, or another agent's sentence is NOT DEMONSTRATED.
- Another agent's claim counts only after I re-derive it from a file or a run; otherwise it is labelled "relayed, unverified".
- Three grades: demonstrated (file cannot serve it), cost-only (file can serve it, at a measured price), not demonstrated.

Standard for a proposal
- Smallest change first; baseline is "change nothing", costed with the same windows.
- Spec text + worked example in the spec's style; classify as later-addition (old rows unchanged, old readers ignore) or row-changing.
- Invariant stated as a sentence a checker can prove from GFA + file, with the planted break that must make it fail.
- Cost is measured on a prototype where possible (bytes, share, build time, peak RSS, reader bytes/requests at 1 kb, 30 kb,
  240 kb, 5 Mb). Anything not measured is labelled BOUND with its derivation.
- Each candidate judged against ADR 0011's trigger/scope/burden as written, quoted with line numbers.
```

How the standard bites on what was actually measured:
- **No hosted file was measured.** Everything ran on single-chromosome builds on ada: MC chr22 (59,120,815 bytes), MC chr6 (82,027,668) and pggb chrY (193,641,445), from `mc22.gfa`, `chr6.gfa` and `pggbY.gfa` (R1, R7, R13). Criterion (a) is met only in that weaker sense.
- **The prototype is a post-pass, not a writer mode.** `walks-additions` reads the GFA and the finished walk file and sizes every candidate at once. Its sizer reproduces the tile and detail bytes of all three files exactly (`analysis.json`, re-checked), so unit sizes are what the writer's compressor would give.
- **Reader probes used graph-walks b7b9349**, before `reader.counts()` existed. A "wrong count" in R24–R26 is a count taken from a cut's trimmed fragments, not the output of the finished call.
- **ADR 0011, for every candidate:**
  - Trigger (0011:165–168): the issues log holds no entry for any candidate (grep of its 2,232 lines).
  - Scope (0011:173–174): chr22 and chr6 are chromosomes of the hosted graph; pggb is not hosted (0011:143).
  - Burden (0011:181–183): "When the evidence is mixed, the format stays."
  - Briefs (0011:184–186): the first agent both built and measured the prototype.
  - Checker evidence (0011:187–188): only C27's check has a recorded failure.

## 1. Complete adjacency

**Need: `demonstrated` for one class of link, `cost-only` for the rest.**
- **Demonstrated: links that only left-out lines walk.** A left-out line has no rows (spec:176–178), so no set of rows holds these.
  - chr22: 32,347 of 4,737,114 links (0.68%, derived); links no line walks: 0 (R1).
  - At chr22:11,816,742–11,846,742 the cut with every piece expanded lacks 4,122 such links at loaded nodes (R25).
  - chr6: 0 of both kinds (R7), so not demonstrated there.
  - 150 random 1 kb chr22 windows: 0 (totals line of `reader/join.mc22.1kb.jsonl`).
  - pggb chrY: 1,700,646 left-out-only and 23 unwalked (R13).
- **Cost-only: links walked from pieces filed elsewhere.**
  - In 150 × 1 kb windows, 11 windows and 13 of 7,828 off-reference nodes lack a link. A cut widened by 150 kb each side finds every one, at 55,224,096 bytes and 2,049 requests over the 150 windows (R24). That is 368,161 bytes and 13.7 requests per window against 29,901 and 1.2 (derived).
  - The cost is not bounded by widening. At the 11.8 Mb window the widened cut still lacks 83,465 links that file lines walk (T72; R25 notes the cut's trimming is part of this). Off-reference nodes are listed by tiles over 1 Mb apart: 2,972 on chr22, 0 on chr6 (R27).
  - Certifying completeness by reading means reading the sequence (bound: no row names the far tiles).
- **Against the need:**
  - The one decomposition prototyped gives the same 430,246 site intervals on chr22 from walked links alone as from all links. Two sites differ in content, by 14,642 nodes and 32,347 links, which are exactly what only left-out lines hold (R30, T46).
  - No consumer view was shown to change.

**Smallest change, inside the file** (unit kind, legal under spec:544–548):

```
#unit  R#0#chr  0  20  links  0
R#0#chr  0  20  links  2,0,0,2,6,4,0,4  2,4,12,2,4,-10,2,-4
```

> A `links` unit is named by its tile's start and has the tile's extent. Its one row, `seq start end links from to`, lists every L line of the GFA with an end on a node of the tile's `ref` rows or `nodes` row, once each, the way round with more `+` ends (the smaller first handle on a tie), in order of `from` then `to`. `from` is handle delta tokens, the first from 0; each `to` token is `2 × (id − its from id) + r`. `.` for none.

- **Worked example** (g4 fixture, tile 0, nodes 1, 2, 7; `g4/out/add.links.txt`, decoded by hand): `1+>2+ 1+>3+ 1+>7+ 2+>3+ 5+>7+ 7+>2+ 7+>8+ 9+>7+`. The cut of the whole g4 file lists 10 links and lacks `1+>3+` (no line walks it) and `9+>7+` (only left-out line U walks it) (`g4/g4.probe.txt`).
- **Invariant and break:** the unit holds every L line with an end at a listed node and no other; a checker with the GFA recomputes it; dropping `1+>3+` must fail it. No such checker exists.

**As a side file:** the same units and table in `<prefix>.<sample>.walks.links.gz` plus `.idx`, with the header of candidate 5. Prototyped as `g4/g4.R.walks.links.gz`.

**Old and new readers:**
- **Old reader, new file (in-file form):** 60 of 60 chr22 cuts identical with links, counts and sites units all added; existing units byte-identical (R22, T77). The table read at open grew from 46,338 to 84,628 bytes, seen as +38,290 bytes on one cut (T78).
- **New reader, old file:** finds no `links` entry in the table and must not claim completeness. ADR 0012:252 rejected inferring a missing unit from a table once.
- **Old checkers on the repacked file:** not run.

**Cost:**

## 2. Bubble or site decomposition

**Need: `cost-only`.** The view is collapsing at zoom-out and a 5 Mb locus (reader behaviour in R29). The decomposition is derivable from rows the file holds: same intervals from walked links alone (R30). Whether a reader can derive it from one cut's rows was not measured; open-problems:814 says so (relayed, unverified).

**What was prototyped is flat, not PangyPlot's nested bubbles and chains.** An anchor is a node the reference passes once. A cut anchor is one that no link and no off-reference component passes over. A site is the stretch between consecutive cut anchors with anything inside.
- **chr22:** 430,246 sites, median 2 interior nodes; 396,032 have exactly two routes (derived from `mc22/sites.tsv`).
  - 10 sites hold 54.1% of all interior nodes.
  - The widest runs 18,171,343–24,637,872 (504,777 nodes).
  - The one with most nodes is 11,814,094–11,916,928 (544,224 nodes). R30's "largest" is the widest, not this one.
  - 852 sites span more than one tile (R30, T39).
- **pggb chrY:** 6 sites, one covering chrY:2,780,000–56,888,000 with 3,961,192 off-reference nodes. The definition says nothing there (R31).

**Smallest change, inside the file:**

```
#unit  R#0#chr  0  20  sites  0
R#0#chr  0  60  site  >1  >6  7  70  12  40,50,60  1,1,1
```

> A `sites` unit is named by the tile its sites start in. A row, `seq start end site left right nodes bp links routeBp routeLines`, is one site: its two cut anchors, the nodes, bp and links between them, and for each distinct route between the anchors its bp and how many lines take it, most-taken first.

- **Worked example** (g4): all of g4 is one site, because node 7 sits in both small bubbles. Three routes of 40, 50 and 60 bp, one line each.
- **Unresolved in the prototype:** a site is filed once, under its start tile, so a window inside a multi-tile site does not find it. It would need the departure pyramid's filing.
- **Naming:** route counts are lines, not haplotypes; one site has 466 traversals for 464 haplotypes (T39). The prototype's summary calls routes "allele_classes".

**As a side file:** same units; 6,585,438 bytes on chr22 (R23).

**Cost:**

## 3. Per-node and per-link haplotype counts

**Need: `cost-only`.**
- **At KIV-2, chr6:160,616,004–160,646,753 (R26, R28):**
  - Unexpanded cut: 311,711 bytes, 4 requests; 13,709 of 14,929 off-reference counts short.
  - Expanded cut: 2,315,808 bytes, 292 requests, 4,784 ms; 128 of 18,955 short.
  - All 128 are one line, `NA18983#1#JBHDWU010000104.1`, whose rows are in a tile the window reads. The cut trims its leading 63,976 bp (T105–T107). So the file serves it; the old cut does not.
- **On reference nodes:** 0 wrong in all 211 probed windows (join totals, T104).
- **Off the reference, chr22:**
  - 14 of 7,828 short in 1 kb windows; 0 after widening by 150 kb (R24).
  - Three of ten affected 30 kb windows stay short after widening (R25).

**What stored counts would give beyond `reader.counts()`** (graph-walks-counts README:724–788, read, not run):
- The reader says "N of M haplotypes step this node" only for a node the reference passes once on the drawn stretch, and a link between two such.
- For every other node it says "at least N" and nothing more.
- A stored count would let "N of M" be said for every listed node, without expanding detail.
- Certifying that by reading is unbounded (R27, as in candidate 1).

**What the prototype's count is:**
- Haplotypes with a line in the file that step the node. Left-out lines are not counted (prototype source lines 589–594).
- M is 464 on chr22 and chr6, the reference plus 463 `#haplotype` lines.
- chr22 has 50,890 nodes a left-out line visits (R1). Whether any count would differ with those lines counted was not computed.

**Smallest change, inside the file. Three forms were sized.**

```
#unit  R#0#chr  0  20  counts  0
R#0#chr  0  20  counts  1,1,5  3,3,2
```

> A `counts` unit is named by its tile's start. Its row, `seq start end counts ids n`, gives for each node of the tile's `ref` rows and `nodes` row, in ascending id as deltas from 0, how many of the file's haplotypes step it.

- **Unit form example:** nodes 1, 2, 7: 3 of 3, 3 of 3, and 2 of 3 haplotypes step them.
- **Tag form:** `hc:Z:` on `ref` and `nodes` rows. This rewrites every tile's bytes, and every reader fetches it.
- **Per-link form:** a third list on a `links` row, e.g. `2,0,1,3,1,1,1,0` on g4 tile 0.

**As a side file:** 1,888,011 bytes on chr22 (R23).

## 4. Stored layout coordinates

**Need: `not demonstrated`.** Criterion (c) cannot hold: a coordinate is a layout tool's output, not a fact of the GFA. The instability figures are another study's (`continuity/out/tables.md`, T57) and were not re-derived: relayed, unverified.

**The whole-chr22 run, finished this session.** On ada I ran the first agent's `crop.py` and `layoutsize.py` unchanged, plus a renderer of mine in pure Python, since ada has neither numpy nor matplotlib (T99).

**Layout cost (L1):**
- `odgi layout -t 8`: 10:02:39 wall, 284,037 s user, 785% CPU, peak 49,045,944 KB, exit 0.
- Before it: GFA conversion 228.5 s; `odgi build` 184.1 s at 15,054,268 KB; `odgi sort -O` 12.8 s.
- Against the writer's 45.7 s and 1,096,920 KB for the same chromosome, that is about 790 times the time and 45 times the memory (derived).
- Result: `mc22.lay` 109,054,482 bytes (34.9 per node), TSV 284,771,387 (91.2 per node), for 3,122,495 nodes.

**Bytes as rows (L8):** one row of four delta lists per tile over the tile's 2,579,409 node listings.
- 6,782,095 bytes at 1 layout unit: 2.63 per node, 11.47% of the walk file.
- 10,978,501 bytes at 0.1 unit: 4.26 per node, 18.57%.
- Detail-only nodes are not included.
- For comparison: the KIV-2 slice took 2.04 and 3.62 per node, PangyPlot's chrY 3.87 and 5.64 (R33, R34).

**Fetch, computed (L9, 1 unit):** 8,172 / 17,330 / 140,265 at 1 kb; 13,266 / 38,951 / 171,930 at 30 kb; 39,157 / 79,322 / 302,696 at 240 kb; 685,382 / 1,467,425 / 1,600,324 at 5 Mb. That is about 28–30% on top of the baseline median (derived).

**Not reproducible (R33, KIV-2 slice):** two runs with the same options share 0 of 51,126 points. Two 8-thread... two 4-thread runs differ by a 2.2° turn; two 1-thread runs are mirror images.

- **Drawn length is not bp.**
  - At 22.03 Mb two adjacent 1 bp reference nodes are drawn 12,163 and 11,634 units long and form the straight side of the teardrop.
  - There, 169 of 955 window reference nodes are drawn above 5 units per bp and hold 65% of the reference's drawn length.
  - At 18.66 Mb ten 1,024 bp nodes hold 47%.
  - Whole chromosome, sampled: 0.705 / 1.119 / 15.874 units per bp (L2).
- **Nodes from elsewhere in the box.**
  - Reference from far away never lands in a box: every other reference node in a box lies within 28,512 bp of its window. Such neighbours take 1.4–11.5% of drawn length.

## 5. Pairing rule for a side file

**Need: `not demonstrated` on a hosted file; shown on a fixture.** No side file is hosted, so criterion (a) cannot hold. It becomes necessary the moment any side-file form above ships.
- `pair/a.gfa` and `pair/b.gfa` have the same segments and different links and walks. Their `#walks` lines are identical, `graph:Z:f2051b87a7f82fcf leftout:i:1`; only `bytes:i:` differs, 676 against 643 (R32, re-read from `pair/*.idx`).
- Two `--refs` of one GFA differ here only in `leftout` (1 against 0, T63). Nothing forces even that, and `#walks` names no reference.

**Smallest change, as the prototype wrote it** (`g4/g4.R.walks.links.gz`, T62):

```
#side  format:i:1  kind:Z:links
#of  format:i:8  tile:i:20  …  graph:Z:f2051b87a7f82fcf  leftout:i:1  bytes:i:676
#reference  R
```

> A side file's header copies line 1 of the walk file's directory whole, `bytes:i:` included, as `#of`, and the walk file's `#reference` line. A reader uses the side file only when both equal the walk file's.

**Inside the walk file:** nothing is needed. A stronger identity, such as a hash of the rows as a `#walks` tag, is a legal later addition but changes every walk file's header. Not prototyped.

**Limit (bound):** two walk files with the same segments, options, left-out count, reference and length but different rows would pair. Not measured how likely.

**Cost:**
- 0 bytes in the walk file.
- 169–171 compressed bytes of side header (R23, T77).
- Fetch (bound): the side file's own directory, header and table at open. Tables are 13,754 / 13,731 / 9,012 bytes on chr22 for links, counts and sites (R23).

**Freezes:** the three header lines and what counts as the same file.

**Does not solve:** a stale side file of equal length; pairing with the node and link index.

**Routes that avoid it:** in-file forms need no pairing; a versioned file name (spec:1184).

## 6. C27 as a guarantee readers may rely on
