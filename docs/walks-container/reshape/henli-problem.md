# Verdict: reshape, not replace

Format 7's core — one file per reference, 64 kb tiles, the reference path per tile, a per-tile route dictionary, a per-haplotype choice row — is the right abstraction for a reference-coordinate browser on a static host, and it is the measured winner. What is wrong is the scope: half of the format's mechanisms exist to make a collapsed-repeat pggb graph look like it has reference coordinates, and by the project's own measure that projection is mostly wrong. Cut that, rename what remains in alignment terms, and the design is sound.

# Reasoning

**What the data is.** A browser window asks "which haplotypes are here, where do they follow GRCh38, where do they differ, and which of them share each difference." That is a multiple alignment of ~470 haplotypes to the reference, with non-reference segments labelled so shared insertions draw once. Node ids are those labels. A walk file is a multi-haplotype GAF sliced into 64 kb tiles with a per-slice dictionary, which is exactly a BAM/CRAM-shaped answer: file by reference position, slice, compress within the slice. Heng Li built tabix for the static-host constraint; projection by reference coordinate is the only way to serve region queries from range requests, so "project all walks onto one reference, tile by tile" is right, not a hack.

**Alternatives, by numbers.**
- *GBZ/GBWT server or WASM:* GBZ is 5.7 GiB with bases (gbz-comparison.md) and has no range-fetchable random access; gbz-base, the honest attempt, is 10 GB and 18–43 round trips per window against one index read plus one range. `vg chunk`/`odgi extract` need a server. Out unless the static-host requirement is dropped.
- *impg / per-haplotype PAF with cs:* measured locally on the maize NAM graph (25 haplotypes, 450 kb, `/tmp/claude-1001/-home-cdiesh-src-gfa-to-tabix/855f6c54-d3d1-4821-8cae-70124fa629a0/scratchpad/henli-problem/scripts/perhap.py`): cs-style rows per haplotype per tile are 116 KB gz against format 7's route+walk 22.5 KB, 5×, and they lose node identity unless node ids are kept, at which point they are GAF. impg's transitive projection also needs the all-vs-all PAF, not a browser artefact.
- *Subgraph per tile, no route dictionary (per-haplotype delta step rows):* 47.6 KB against 22.5 KB at N=25, 2.1×; ADR 0010's Srel/Sabs measured 3.1–4.5× at N=463. Choices grow as N^0.86, steps as N. The dictionary earns its keep.
- *rGFA bubbles + per-haplotype allele calls, VCF-like:* this is the native review's site rows. On MC it is 25 vs 29 KB at 1 kb and a 20% smaller file, but the p90 is 121 vs 53 KB and the 1 Mb tail 3 MB vs 1.4 MB, and 60% of pggb departures need a visit index that does not exist (11 of 60 windows wrong). It is the same route dictionary keyed by breakpoint instead of by tile. Not worth the switch.
- *Format 7 with reader fixes, Tabix at chunk span, 16 kb tiles, uncut departures:* all measured in ADR 0010 and arbA, all lose.

**Which mechanisms are projection artefacts.** Not the projection's: the ref row, nodes, routes, walk choices, the byte-range table, and a size cap for satellites (abridged/detail). Every alternative above needs the last. Pure pggb artefacts: placement of revisited nodes, `--stay`, `@k`/`:k` copy naming, and most departure records. On pggb chrY: 107,467 revisited nodes, 299,916 copies named, 110,886 detail rows, 425,040 departure records of which 97% have an end on a revisited node and 87% carry 0 own bp, one haplotype with 2,065 records in one 64 kb window; and only 35.9% of pieces land within 10 kb of where the MC graph places the same contig position (open-problems.md). On MC (`revisited:i:0`) every one of these mechanisms is inert: 0 copies named, 24,648 departure records of which 95.7% are a bubble across a tile edge. The file for the graph that is reference-exact is 59 MB and 29 KB per 1 kb window; the file for the graph that is not is 188 MB and 70 KB, and much of that is machinery describing choices the writer made.

Placing a haplotype by node identity in a graph where the reference walks one node 50 times is deriving a coordinate from something that does not have one. A haplotype sequence aligned to the reference sequence has a unique coordinate; the collapsed graph does not. HPRC publishes MC graphs on both references, and pggb's own wfmash PAFs exist.

# Minimal design, what it costs, what it keeps

Keep from format 7: file per reference, 64 kb tiles, `ref`/`nodes`/`route`/`walk` rows, delta ids and the dictionary inside a tile, the unit table, abridged pieces with a detail unit. These are the measured core.

Change:
- **Reference-exact only.** Require every tile's placement to be a fact of the graph: write placement from node identity only where the reference passes a node once, and otherwise from an alignment of the haplotype to the reference (the MC build on that reference, or a PAF), never from a nearest-pass rule. Delete `--stay`, `@k`/`:k`, `passes`, `leavePasses`/`rejoinPasses`, and the "exact and chosen" section. On MC this changes zero bytes. On pggb it removes 299,916 named copies and most of 425,040 departure records; unmeasured this run (ada down), but the per-row counts above say the file falls toward MC's shape. What it loses: a pggb graph with no alignment gets no walk file, instead of a wrong one.
- **Departures as SAM-style neighbour fields** on the walk row: `prev seq:pos:strand:ownGap`, `next ...`, so each line states where its piece came from and went, decodable alone, no second record kind for the common case. Keep the pyramid only for its one real job, windows inside a span a haplotype skips, as a separate `gap` unit kind — and call it what it is, a binning index over gap intervals. Expected cost: a few bytes per walk row; MC departure rows today are a rounding error (459 gz bytes of 47 KB on maize).
- **Table per sequence.** 183 KB of the 211 KB first view is the whole-genome unit table. A root table of sequences pointing at per-sequence tables (PMTiles-style, already in prior-art-review) makes chr22's open about 8 KB and total first view roughly 40 KB.

Estimated result: identical bytes per window and file size on MC (29 KB at 1 kb, 59 MB chr22), a materially smaller pggb file with every stated position true, three fewer mechanisms, a spec that reads as "GAF per haplotype per tile, dictionary-compressed," and one honest limitation in place of a placement rule.
